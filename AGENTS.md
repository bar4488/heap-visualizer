# Project Workflow

Keep process lightweight. Spend time on the product, not repository ceremony.

## Before changing code

- Check `git status` and preserve work you did not create.
- Read the relevant implementation and tests. Use `docs/context.md` for build,
  run, and test commands.
- Treat `spec/` as the source of truth for product behavior. Update it when the
  intended behavior changes.

## While working

- Make the smallest coherent change that solves the request.
- Follow existing structure and style; do not introduce a parallel source of
  truth for domain behavior.
- Keep handwritten source in `src/`. `dist/` is generated by `build.sh`.
- Update documentation only when commands, public behavior, architecture, or an
  important operational constraint changed.
- Tickets, explorations, decision records, status updates, and work logs are
  optional tools. Create or update them only when they materially help the work.
- Do not add browser automation or new dependencies unless the task requires
  them.

## Verification

Run the checks relevant to the files changed. Common commands are:

```sh
cargo test --manifest-path src/core/Cargo.toml
cargo test --manifest-path src/filter-dsl/Cargo.toml
cargo test --manifest-path src/local-server/Cargo.toml
cargo clippy --manifest-path src/local-server/Cargo.toml --all-targets --no-deps -- -D warnings
node --test 'src/web/**/*.test.ts'
node_modules/.bin/tsc -p tsconfig.test.json
python3 -m unittest discover -s src/server
./build.sh
```

Use `source "$HOME/.cargo/env"` first when Cargo is not on `PATH`. Report what
was run and any meaningful coverage gap.

## Safety and Git

- Never discard or overwrite unrelated user changes.
- Avoid destructive Git or filesystem commands.
- Do not push unless the user asks.
- Commits and documentation bookkeeping are not required unless the user asks
  for them or they clearly improve the deliverable.
